# Stage 10 — 웹

> **선행**: Stage 9 완료 (또는 Stage 8까지만 완료해도 착수 가능)
> **브랜치**: `stage-10-web`
> **목적**: 데스크톱에서 일정을 보고 편집한다. 앱과 같은 데이터를 쓰되, **UI는 웹에 맞게 새로 만든다.**

---

## 0. 핵심 결정: react-native-web을 쓰지 않는다

Expo는 `expo export --platform web`으로 웹 빌드를 뱉을 수 있다. 하지만 **그렇게 하지 않는다.**

이유:
- 캘린더의 웹 UX는 모바일과 근본적으로 다르다 — 마우스 드래그로 시간 블록 생성, 넓은 주간 뷰, 키보드 단축키, 우클릭 메뉴
- react-native-web으로 뽑으면 "모바일 앱을 브라우저에서 보는" 결과가 나온다. 데스크톱에서 쓰기엔 답답하다
- 우리는 Stage 1부터 `src/domain/`을 순수 TS로 유지해왔다. **이걸 쓰려고 그렇게 한 것이다**

### 구조

```
apps/
  mobile/     기존 Expo 앱
  web/        새 Vite + React
packages/
  domain/     ← src/domain/을 여기로 이동. 양쪽이 import
  data/       ← Supabase 쿼리/타입. 양쪽이 import (RN 의존 제거 필요)
```

pnpm workspace로 모노레포 전환. **이 리팩터링이 이 스테이지의 첫 작업이자 가장 위험한 부분**이므로, 별도 커밋으로 분리하고 앱이 그대로 동작하는지 먼저 확인한다.

## 1. 작업 순서

### 1-1. 모노레포 전환

1. pnpm workspace 설정
2. `src/domain/` → `packages/domain/` 이동. 앱에서 `@chrona/domain`으로 import
3. **앱을 빌드해서 아무것도 안 깨졌는지 확인** ← 여기서 멈추고 검증
4. `src/data/`를 옮길 수 있는 부분과 없는 부분으로 분리
   - Supabase 쿼리·매퍼·타입 → `packages/data/` (RN 의존 없음)
   - AsyncStorage persist, netinfo → 앱에 남김 (플랫폼 의존)
5. 다시 빌드 확인

**domain 이동이 잘 되는 이유는 Stage 1부터 린트로 RN import를 막아왔기 때문이다.** 만약 새어 들어간 게 있으면 여기서 드러난다.

### 1-2. 웹 앱 스캐폴딩

```
Vite + React + TypeScript
TanStack Query (앱과 동일)
Tailwind CSS 또는 CSS Modules
react-router 또는 TanStack Router
```

- 디자인 토큰은 `packages/domain/tokens.ts`로 옮겨서 공유하거나, CSS 변수로 재정의
- **색상값이 앱과 어긋나지 않도록** 단일 소스에서 생성

### 1-3. 인증

- Supabase 매직링크 (앱과 동일 계정)
- 세션은 localStorage
- 리다이렉트 URL을 Supabase 설정에 추가

### 1-4. 웹 전용 UX

**앱을 그대로 옮기지 않고, 데스크톱에서 진짜 편한 것을 만든다.**

| 기능 | 웹에서의 형태 |
|---|---|
| 주간 뷰 | 넓은 7일 타임그리드가 기본 (모바일은 월간이 기본) |
| 일정 생성 | **빈 시간대를 드래그하면 즉시 생성** |
| 일정 이동 | 드래그 앤 드롭으로 시각·날짜 변경 |
| 일정 길이 | 하단 가장자리 드래그로 리사이즈 |
| 편집 | 사이드 패널 (모달보다 빠름) |
| 단축키 | `n` 새 일정 / `t` 오늘 / `←→` 이동 / `1` 일 `2` 주 `3` 월 / `/` 검색 |
| 우클릭 | 복제 / 삭제 / 색상 변경 |
| 시간표 | 넓은 격자, 드래그로 블록 생성 |
| 통계 | 큰 화면 활용해 4개 지표 한눈에 |

### 1-5. 웹에서 만들지 않는 것

- **알람 기능 일체.** 브라우저 알림은 전체화면도, 끌 때까지 울리지도 못한다. 알람 설정은 **표시만 하고 편집도 가능하되, 웹에서는 울리지 않는다**는 안내를 명시
- 집중 타이머 — 만들어도 되지만 우선순위 낮음
- 위젯

### 1-6. 데이터 정합성

- 같은 Supabase를 보므로 `updated_at` last-write-wins가 그대로 적용 (마스터 §7.3)
- 웹에서 수정 → 앱이 포그라운드 진입 시 재계산되면서 알람도 갱신됨
- **웹에서 일정을 바꿔도 앱을 한 번 열기 전까지는 알람이 갱신되지 않는다.** 이건 구조적 한계이며, 웹 UI에 안내 문구를 넣는다
  - (개선하려면 Supabase Realtime + FCM 푸시가 필요한데, 개인용 앱에 과한 복잡도다)

### 1-7. 배포

- Vercel 또는 Cloudflare Pages 무료 티어
- 개인용이므로 Supabase Auth로만 접근 제한하면 충분
- 커스텀 도메인은 선택

## 2. 검증

| # | 항목 | 통과 기준 |
|---|---|---|
| 1 | 모노레포 전환 후 앱 빌드 | 기존 기능 전부 동작 |
| 2 | 웹 로그인 | 앱과 같은 계정 |
| 3 | 웹에서 일정 생성 | 앱에 반영 (앱 재진입 시) |
| 4 | 앱에서 생성 | 웹에 반영 (새로고침) |
| 5 | 드래그 생성 | 정확한 시각에 생성 |
| 6 | 드래그 이동/리사이즈 | 저장됨 |
| 7 | 반복 일정 3지선다 | 웹에서도 동작 |
| 8 | **종일 일정** | 앱과 날짜 일치 (시간대 버그 없음) |
| 9 | 단축키 | 전부 동작 |
| 10 | 웹 수정 → 앱 알람 갱신 | 앱 포그라운드 진입 후 반영 |
| 11 | 통계 | 앱과 수치 일치 |

**8번과 11번이 domain 공유가 제대로 됐는지 증명하는 항목이다.** 앱과 웹이 다른 숫자를 보여주면 domain이 아닌 곳에 로직이 있다는 뜻이다.

## 4. 사용자에게 물어야 할 것

1. 모노레포 전환을 감수할지, 아니면 웹에서 domain을 복사해 쓸지 (복사는 나중에 반드시 어긋난다 — 비권장)
2. 배포처 (Vercel / Cloudflare Pages)
3. 웹에서 우선순위가 높은 기능 (주간 뷰 / 시간표 / 통계 중)
