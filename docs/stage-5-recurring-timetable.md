# Stage 5 — 반복 일정 + override + 시간표 모드

> **선행**: Stage 4 완료 및 머지
> **브랜치**: `stage-5-recurring-timetable`
> **목적**: 프로젝트에서 **논리적으로 가장 어려운 부분**. 반복 일정을 제대로 구현하고, 그 위에 시간표를 얹는다.

---

## 0. 왜 어려운가

"매주 화요일 9시 수업"을 100개 행으로 펼쳐 저장하면 안 된다. 대신 규칙만 저장하고 조회 시 전개한다. 그러면 **"이번 주만 휴강", "다음 주만 시간 변경"**을 어떻게 표현할 것인가가 문제가 된다. 이게 `event_overrides`의 존재 이유다.

여기서 대충 만들면 알람이 휴강한 수업에 울리거나, 수정한 회차가 원상복구되는 버그가 나온다.

---

## 1. 작업 순서

### 1-1. rrule 전개 (`src/domain/recurrence.ts`)

**순수 함수. `rrule` 패키지만 의존.**

```ts
expandRule(
  rrule: string,          // 'FREQ=WEEKLY;BYDAY=TU,TH'
  dtstart: Date,
  until: Date | null,
  range: { from: Date; to: Date },
  tz: string,
): Date[]
```

주의사항:
- **DTSTART의 시간대 처리.** `rrule` 패키지는 UTC 기준으로 동작하므로, 한국 시간 09:00을 그대로 넣으면 서머타임이 없는 한국은 괜찮지만 웹(Stage 10)에서 어긋날 수 있다. `date-fns-tz`로 명시적 변환 후 넣는다
- 종일 반복 일정은 `date` 기준으로 전개 (시각 개입 금지)
- 전개 범위는 항상 유한하게. `until`이 없어도 `range.to`로 잘린다

### 1-2. override 병합 (`src/domain/recurrence.ts`)

```ts
applyOverrides(
  occurrences: Occurrence[],
  overrides: EventOverride[],
): Occurrence[]
```

규칙:
- `original_start`로 회차를 식별한다 (밀리초까지 정확히 일치해야 함 → **전개 결과와 저장값의 정밀도를 통일**할 것)
- `is_cancelled` → 해당 회차 제거
- `new_start`/`new_end` → 시각 교체. **이동한 회차가 range 밖으로 나가면 제거, 밖에서 안으로 들어오면 추가**
- override는 원본 event의 다른 속성(제목·색)을 바꾸지 않는다. 시각과 취소만 다룬다 (범위를 넓히면 복잡도가 폭발한다)

**단위 테스트 필수:**
```
매주 화요일 5회 전개
  → 3번째 회차 취소 → 4개
  → 2번째 회차를 수요일로 이동 → 순서 재정렬 확인
  → 마지막 회차를 range 밖으로 이동 → 제외
  → range 밖 회차를 안으로 이동 → 포함
```

### 1-3. 반복 편집 UX (★ 여기서 사용자가 헷갈린다)

반복 일정을 수정/삭제할 때 **반드시 3지선다를 물어본다:**

```
이 일정을 수정합니다
  ○ 이 일정만
  ○ 이후 모든 일정
  ○ 모든 일정
```

각각의 처리:
| 선택 | 처리 |
|---|---|
| 이 일정만 | `event_overrides`에 행 추가 |
| 이후 모든 일정 | 원본의 `rrule_until`을 직전 회차로 자르고, **새 event를 그 시점부터 생성** |
| 모든 일정 | 원본 event 수정. 기존 override는 유지 여부를 확인 |

삭제도 동일한 3지선다. "이 일정만" 삭제 = `is_cancelled` override.

**"이후 모든 일정"이 가장 까다롭다.** 원본을 자르고 새 event를 만들 때 reminders도 복사해야 한다.

### 1-4. 반복 설정 UI

```
반복  [안 함 ▾]
      · 안 함
      · 매일
      · 매주 (요일 선택)
      · 격주
      · 매월 (날짜 / n번째 요일)
      · 사용자 지정
종료  [안 함 / 날짜 지정 / N회 후]
```

- 선택 결과를 rrule 문자열로 직렬화. 역파싱해서 UI로 복원도 되어야 한다
- 자연어 미리보기 표시: "매주 화, 목 · 2026년 12월 20일까지"
- 사용자 지정은 `INTERVAL` + `BYDAY` + `BYMONTHDAY`까지만 지원. 그 이상은 안 만든다

### 1-5. 캘린더/알람에 연결

- Stage 3의 `expandOccurrences`가 이제 진짜로 rrule을 쓴다 (pass-through 제거)
- 재계산 시 override 반영 확인 — **마스터 §3.7의 2번 단계**
- 캘린더 그리드는 표시 범위만 전개한다. 전체를 전개하면 스크롤이 버벅인다
- 전개 결과를 `useMemo` + 쿼리 캐시에 보관. 매 렌더 재전개 금지

### 1-6. 학기 관리 (`semesters`)

```
/semesters (더보기 하위)
  2026-2학기  2026.09.01 ~ 2026.12.20   [활성]
  2026-1학기  2026.03.02 ~ 2026.06.21
  [+ 학기 추가]
```

- 활성 학기가 시간표 탭의 기본 표시 대상
- 학기 종료일이 시간표 과목의 `rrule_until`이 된다
- 학기 복사: 기존 학기의 시간표를 새 학기로 통째 복제 (제목·요일·교시 유지, 날짜만 새 학기 기준으로)

### 1-7. ★ 시간표 탭 (`/(tabs)/timetable`)

```
┌─────────────────────────────────────┐
│ 2026-2학기 ▾        [알림 일괄 ▾]    │
├────┬────┬────┬────┬────┬────────────┤
│    │ 월 │ 화 │ 수 │ 목 │ 금         │
├────┼────┼────┼────┼────┼────────────┤
│ 1  │    │████│    │████│            │
│9:00│    │자료│    │자료│            │
│ 2  │    │구조│    │구조│            │
├────┼────┼────┼────┼────┼────────────┤
│ 3  │████│    │████│    │            │
│    │운영│    │운영│    │            │
└────┴────┴────┴────┴────┴────────────┘
```

- 세로축은 `period_presets`(교시). 시각축이 아니라 **교시축**이다
- 빈 칸을 **드래그하면 블록 생성** → 과목명 입력 모달
- 블록 탭 → 편집, 롱프레스 → 이동/삭제
- 각 과목은 `kind='timetable'`, `rrule = FREQ=WEEKLY;BYDAY=<요일>`, `rrule_until = 학기 종료일`
- 과목 색상은 팔레트 8종에서 자동 배정 (중복 최소화)

**알림 일괄 설정:**
```
[모든 수업 10분 전 알림  ON/OFF]
```
전 과목의 reminders를 한 번에 생성/삭제한다. 개별 조정은 과목 편집에서.

### 1-8. 홈의 "다음 수업" 슬롯 채우기

Stage 4에서 비워둔 자리:
```
다음 수업
┃ 화 1교시 · 자료구조
┃ 내일 09:00 · 새빛관 401
```

## 2. 검증

| # | 항목 | 통과 기준 |
|---|---|---|
| 1 | 매주 반복 일정 생성 | 캘린더에 매주 표시 |
| 2 | "이 일정만" 수정 | 해당 회차만 변경, 나머지 유지 |
| 3 | "이후 모든" 수정 | 이전 회차 유지, 이후만 변경 |
| 4 | "이 일정만" 삭제 | 해당 회차만 사라짐 |
| 5 | **휴강 처리 후 알람** | 해당 회차 알람이 울리지 않음 |
| 6 | 회차 시각 변경 후 알람 | 새 시각에 울림 |
| 7 | 시간표 드래그 생성 | 블록 생성 → 캘린더에도 반영 |
| 8 | 알림 일괄 ON | 전 과목 reminders 생성, 재계산 반영 |
| 9 | 학기 복사 | 날짜만 바뀌고 구조 동일 |
| 10 | 반복 100회 일정 | 캘린더 스크롤 버벅임 없음 |
| 11 | rrule 역파싱 | 저장 후 재편집 시 UI 상태 복원 |

**5번이 이 스테이지의 핵심 검증이다.** 마스터 §3.7이 지켜지는지 확인하는 것.
